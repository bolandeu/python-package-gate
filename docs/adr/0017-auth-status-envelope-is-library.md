# Конверт `auth status` — часть библиотеки секретов, не пакета

Статус: accepted (Человек, 2026-11-19)

Контракт `<cli> auth status [--check] --json` (tools `docs/standard-release.md` §8) существует в трёх независимых
реализациях: `rb-dataio` (`credentials/health.py`, 215 строк), `google_oauth/status.py` (263),
`yandex_oauth/status.py` (248). Совпадает то, что и есть протокол: коды выхода `0`/`3`, `CHECK_TIMEOUT = 10.0`,
`HEALTHY = {"ok", "unchecked"}`, `ALWAYS_PROBLEMS = {"invalid", "expired"}`, `is_problem()`, `_iso`, `_scrub`,
конверт `{tool, version, checked_at, credentials[]}`, девять ключей записи (`provider, required, fields, source,
source_ref, status, expires_at, quota, message`) и словарь статусов `ok | invalid | expired | quota_exhausted |
unreachable | missing | unchecked`. Разошлось шесть вещей, каждая — вывод, который потребитель читает как контракт:
смысл `fields` (объявленные поля / одно поле / фактически найденные), язык `message` (английский в dataio,
русский в двух пакетах авторизации), форма exit 3 (`CredentialsUnhealthy(problems)` в dataio против
`(report, problems)` и ошибки, собранной командой), `source_ref` при смешанных источниках (все места против
только победителя), тип `Health`/`Quota` (три копии с одинаковыми полями) и средства, которых нет ни у кого, кроме
dataio (`per_target`, `public_fields`, `legacy_env` в `source_ref`). Пока форма живёт в пакетах, следующий пакет
приносит четвёртый вариант — как это уже случилось с хранением секрета до `rb-credentials`.

Решили:

1. Общее ядро конверта переезжает в `rb_credentials.status`: `Health`, `Quota`, `is_problem(entry)`,
   `problems(report)`, `exit_code(report)`, `report(tool, version, entries)` и `entry(...)` — скелет записи со
   `_scrub` и `_iso`. Это одна реализация на весь набор пакетов; пакеты реэкспортируют `Health`/`Quota` под
   прежними именами, чтобы `providers/base.py` и `health_check()` не меняли сигнатур.
2. В библиотеку не переезжают `credential_status()` и `health_check()`: они читают раскладку своего хранилища и
   зондируют свой API. Пакет объявляет провайдера (`name`, `credential_fields`, `required`), сам ищет поля и сам
   делает живой запрос, а из библиотеки берёт скелет записи, конверт и правила проблем. Инструмент после перехода
   содержит только провайдеров и `health_check()`.
3. `fields` — объявленные обязательные поля провайдера, всегда в объявленном порядке. «Фактически найденные» поля
   (как в `yandex_oauth`) делают запись зависящей от машины: две машины дают разные `fields` при одинаковом
   результате.
4. `message` — английский, свободный текст; потребитель его не разбирает, единственное правило — секретов в нём нет
   (`scrub`). Русские сообщения `google_oauth`/`yandex_oauth` переводятся при переезде на библиотеку.
5. Exit 3 библиотека не бросает: `report()` и `problems()` возвращают данные, ошибку `CREDENTIALS_UNHEALTHY`
   собирает команда пакета из своего класса `CliError`. Библиотека секретов не зависит от типов ошибок инструмента.
6. `source_ref` перечисляет все места, откуда взяты поля (`<var>`, `<var>; rest from keychain service <ns>:<name>`,
   `<var>; rest from key file ...`), `source` называет победителя (`env` | `keychain` | `file`). Форма dataio:
   она строго информативнее «только победителя» и уже проверена снапшотами.
7. Остаётся в пакете: перечисление записей `per_target` (читает индекс своего хранилища), `public_fields`
   (передаётся в `entry()` списком), учёт `legacy_env` и `shared_namespaces` (складывается в готовую строку
   `source_ref`), человеческий вывод (`render`).

Порядок перехода: этот ADR → `rb_credentials.status` с тестами на все шесть решений → перевод
`google_oauth`/`yandex_oauth` (их `status.py` становятся тонкой обёрткой над библиотекой) → вычистка копий в
пакетах, первым `rb-dataio`. Форма конверта замораживается снапшот-тестом на текущий `auth status --json` (полный
JSON плюс коды выхода) до подмены реализации, а не после.

Рассмотренные варианты: оставить три копии и договориться текстом §8 (не работает — расхождения уже есть, а
текст их не ловит); вынести в библиотеку и `credential_status`/`health_check` целиком (библиотека начала бы знать
про файловые ключи Google, refresh_token Яндекса и цели деплоя — против её же правила «адреса остаются у
вызывающего»); сделать отдельный пакет `rb-auth-status` (четвёртый репозиторий ради ~80 строк и ещё одна
зависимость в каждом пакете).
